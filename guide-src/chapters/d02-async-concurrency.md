Concurrency is doing several things at once; parallelism is doing several
things at the same instant. Rust gives you both, with different tools and
different costs. This chapter builds the mental model from the `Future` trait
upward, then shows the practical Tokio patterns. The library's [threads
chapter](#threads), [shared-state chapter](#shared-state), [async
chapter](#async) and [async internals chapter](#concurrency-async-internals)
go deeper into the machine-level story; this chapter is the working engineer's
map.

:::analogy A kitchen, not a photocopier
A **thread** is a second cook: more chopping happens at the same instant, but
each cook needs space and equipment. An **async task** is one cook who starts
the rice, moves to the sauce while it simmers, and returns when the timer
rings. Async does not make the rice cook faster; it stops the cook from
standing still. CPU-bound work belongs on more cooks (threads or a thread
pool). Waiting belongs in one cook's schedule (async).
:::

:::compare Threads and async are tools, not rivals
A thread is a pre-emptive, OS-scheduled stack with its own copy of the stack; an async task is a cooperative state machine polled by an executor. Threads suit blocking work, CPU-bound parallelism and code that is simpler to write imperatively. Async suits many idle connections, cancellation and explicit back-pressure, at the cost of `Send` bounds, pinning and the risk of blocking an executor. Most production services use both: a Tokio runtime for I/O, a bounded blocking pool or Rayon for CPU.
:::


## 2.1 The `Future` trait and `async`/`await`

A **future** is a value representing a computation that may not be finished
yet. The trait has one method:

```rust
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

// The shape of the trait, simplified: the real one also has a default
// `Output` associated type and is implemented for references to futures.
trait MyFuture {
    type Output;
    fn poll(self: Pin<&mut Self>, context: &mut Context<'_>) -> Poll<Self::Output>;
}

enum Poll<T> {
    Ready(T),
    Pending,
}
```

`async fn` is sugar for a function that returns `impl Future<Output = T>`. The
body does not run when the future is created; it runs when the future is
**polled**. `.await` polls a future and, if it is `Pending`, suspends the
current task and returns control to the executor. The compiler transforms the
`async` body into a state machine whose states are the `.await` points.

```rust
async fn fetch_user(id: u64) -> Result<String, String> {
    if id == 0 {
        return Err("missing id".to_string());
    }
    Ok(format!("user-{id}"))
}

async fn greeting(id: u64) -> String {
    match fetch_user(id).await {
        Ok(name) => format!("hello, {name}"),
        Err(error) => format!("error: {error}"),
    }
}

#[tokio::main]
async fn main() {
    println!("{}", greeting(7).await);
    println!("{}", greeting(0).await);

    // A future is lazy: creating it does nothing until polled.
    let pending = greeting(9);
    println!("created but not run");
    println!("{}", pending.await);
}
```

Async is not a runtime and not a thread. The language supplies the state
machine; a **runtime** (Tokio, async-std, smol, embassy for embedded) supplies
the executor, the reactor for I/O and timers, and the task queue. Without a
runtime, `.await` has no driver. `#[tokio::main]` builds a multi-threaded
runtime, blocks on the future and shuts the runtime down when it finishes.

## 2.2 `Pin`, `Unpin` and self-referential structs

The state machine generated by `async` may store a reference to another field
of itself across an `.await` (for example, a slice borrowed from a buffer held
in the same future). Moving that future after it has been polled would
invalidate the internal reference. **`Pin<P>`** is the type that guarantees the
pointee will not move again for as long as the pin exists.

```rust
use std::marker::PhantomPinned;
use std::pin::Pin;

struct SelfReferential {
    value: String,
    pointer: *const String,
    _pin: PhantomPinned, // opt out of Unpin
}

impl SelfReferential {
    fn new(value: String) -> Pin<Box<Self>> {
        let mut boxed = Box::pin(Self {
            value,
            pointer: std::ptr::null(),
            _pin: PhantomPinned,
        });
        let pointer = &boxed.value as *const String;
        // Safe because the value is pinned in the box and never moved.
        unsafe {
            let mut_ref = Pin::as_mut(&mut boxed);
            Pin::get_unchecked_mut(mut_ref).pointer = pointer;
        }
        boxed
    }

    fn value(&self) -> &str {
        &self.value
    }
}

fn main() {
    let pinned = SelfReferential::new("stable".to_string());
    println!("{}", pinned.value());
}
```

`Unpin` is an auto trait for types that are safe to move even after being
pinned; almost every ordinary type is `Unpin`. `!Unpin` types (typically
compiler-generated async blocks) are the ones that need pinning. On stable
Rust, `Box::pin` is the common way to get a pinned future onto the heap;
`tokio::pin!` pins on the stack for use with `select!`; `std::pin::pin!`
creates a pinned local. You rarely implement `Pin` projection by hand: the
`pin-project-lite` crate generates the unsafe projection safely. `Pin<&mut T>`
does not mean the value is immovable forever, only for the lifetime of that
pin. Section 3.4 uses pinning inside a hand-written executor, and the [async
internals chapter](#concurrency-async-internals) shows the generated layout.

:::warn `Pin` is not a heap allocator
A common mistake is to believe `Pin<&mut T>` prevents all moves for the whole
program. It prevents moves through that pinned reference while it exists. Once
the pin is dropped, an owning type such as `Box<T>` may move the box again.
The guarantee is scoped, like a borrow.
:::

## 2.3 The waker and the polling model

An executor needs to know when a `Pending` future can make progress. Each poll
receives a `Context`, which carries a **`Waker`**. The future registers the
waker with whatever will eventually make it ready (a socket, a timer, another
task), and returns `Pending`. When the event happens, the source calls
`waker.wake()`, which puts the task back on the executor's run queue.

```rust
use std::future::Future;
use std::pin::Pin;
use std::sync::{Arc, Mutex};
use std::task::{Context, Poll, Wake, Waker};
use std::thread;
use std::time::Duration;

struct Flag {
    ready: Mutex<bool>,
}

struct ThreadWaker(thread::Thread);

impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) {
        self.0.unpark();
    }
}

impl Future for Flag {
    type Output = ();

    fn poll(self: Pin<&mut Self>, context: &mut Context<'_>) -> Poll<()> {
        let mut ready = self.ready.lock().unwrap();
        if *ready {
            Poll::Ready(())
        } else {
            context.waker().wake_by_ref(); // in a real reactor, store the waker
            Poll::Pending
        }
    }
}

fn block_on<F: Future>(future: F) -> F::Output {
    let mut future = Box::pin(future);
    let waker = Waker::from(Arc::new(ThreadWaker(thread::current())));
    let mut context = Context::from_waker(&waker);
    loop {
        match future.as_mut().poll(&mut context) {
            Poll::Ready(value) => return value,
            Poll::Pending => thread::park_timeout(Duration::from_millis(10)),
        }
    }
}

fn main() {
    let flag = Flag { ready: Mutex::new(false) };
    block_on(flag);
    println!("done");
}
```

This trivial executor spins on a timer; a real reactor stores the waker beside
the file descriptor and calls it from the I/O event loop. The important
invariant is that a future must arrange for **exactly one** wake when it returns
`Pending`. Waking too early causes a busy loop; failing to wake causes a hang.
The `Waker` is cloneable and cheap to pass around. The [async internals
chapter](#concurrency-async-internals) implements a correct single-threaded
executor and explains the `RawWakerVTable` underneath.

## 2.4 Tokio: tasks, `spawn`, `spawn_blocking`, `join!` and `select!`

Tokio's runtime has a multi-threaded scheduler by default. `tokio::spawn`
turns a future into an independent **task**: it must be `'static` and `Send`,
returns a `JoinHandle`, and may run on any worker thread.

```rust
use std::time::Duration;
use tokio::time::sleep;

async fn work(name: &'static str, milliseconds: u64) -> &'static str {
    sleep(Duration::from_millis(milliseconds)).await;
    println!("{name} finished");
    name
}

#[tokio::main]
async fn main() {
    // Concurrent, same task: both run until they yield.
    let (first, second) = tokio::join!(work("a", 30), work("b", 10));
    println!("{first} {second}");

    // Independent tasks: they may run on different worker threads.
    let handle = tokio::spawn(async move { work("spawned", 5).await });
    println!("{}", handle.await.unwrap());

    // First to finish wins; the other is dropped (cancelled).
    let winner = tokio::select! {
        value = work("fast", 5) => value,
        value = work("slow", 50) => value,
    };
    println!("{winner}");

    // Blocking work must not run on the async worker pool.
    let sum = tokio::task::spawn_blocking(|| (1..=1_000_000_u64).sum::<u64>())
        .await
        .unwrap();
    println!("{sum}");
}
```

- **`join!`** polls several futures in the same task and waits for all. It is
  cheap and does not require `Send` or `'static`. `try_join!` returns early on
  the first error and drops the rest.
- **`spawn`** creates a task the runtime schedules independently. A panic in a
  spawned task is returned as a `JoinError` by `await`; it does not abort the
  process.
- **`select!`** waits for the first branch to complete. The other branches are
  dropped, which cancels them at their next `.await`; any partially written
  state must be safe to drop. Use `biased;` to check branches in source order.
- **`spawn_blocking`** moves CPU-bound or blocking work (file I/O without
  Tokio's async wrappers, `std::net`, expensive compression) to a dedicated
  blocking pool. Calling `std::thread::sleep`, a synchronous database driver or
  a long computation directly in an async task starves the runtime.

`#[tokio::main(flavor = "current_thread")]` is a legitimate choice for small
services and tests; it removes the need for `Send` on spawned futures. See
sections 2.14 and 4.29 for the production consequences.

## 2.5 Async channels

Channels move values between tasks without shared memory. Tokio offers four
shapes with different semantics:

| Channel | Producers | Consumers | Behaviour |
| --- | --- | --- | --- |
| `mpsc` | many | one | queue; bounded `send().await` applies backpressure |
| `oneshot` | one | one | single value, often a reply |
| `broadcast` | many | many | every receiver sees every value; lagging receivers get `RecvError::Lagged` |
| `watch` | many | many | receivers see the latest value only; ideal for configuration and shutdown |

```rust
use tokio::sync::{broadcast, mpsc, oneshot, watch};

async fn worker(mut jobs: mpsc::Receiver<u32>, replies: mpsc::Sender<u32>) {
    while let Some(job) = jobs.recv().await {
        replies.send(job * 2).await.unwrap();
    }
}

#[tokio::main]
async fn main() {
    let (job_tx, job_rx) = mpsc::channel(8);
    let (reply_tx, mut reply_rx) = mpsc::channel(8);
    let worker = tokio::spawn(worker(job_rx, reply_tx));

    for value in 1..=3 {
        job_tx.send(value).await.unwrap();
    }
    drop(job_tx); // closes the queue, so the worker loop ends
    while let Some(value) = reply_rx.recv().await {
        println!("reply {value}");
    }
    worker.await.unwrap();

    // oneshot: a request/reply pair.
    let (tx, rx) = oneshot::channel();
    tokio::spawn(async move { tx.send("pong").unwrap() });
    println!("{}", rx.await.unwrap());

    // watch: state that must not queue up.
    let (state_tx, mut state_rx) = watch::channel(0_u32);
    state_tx.send(1).unwrap();
    state_tx.send(2).unwrap();
    println!("latest {}", *state_rx.borrow_and_update());
    println!("changed {}", state_rx.changed().await.is_ok());

    // broadcast: every subscriber sees every message.
    let (event_tx, mut event_rx) = broadcast::channel(16);
    event_tx.send("started").unwrap();
    println!("event {:?}", event_rx.recv().await);
}
```

Bounded channels are the default in production because they make overload
visible: `send().await` waits, which lets the producer slow down. An unbounded
channel turns overload into memory growth and eventual OOM. `watch` coalesces
intermediate values, so it is right for "the current configuration" and wrong
for "every order". `broadcast` reports lag rather than silently dropping
messages; decide whether a lagging listener should resynchronise or restart.
Section 2.9 covers the standard-library channels, which are synchronous and
blocking.

## 2.6 Streams and sinks

A `Stream` is the asynchronous analogue of `Iterator`: it yields
`Poll::Ready(Some(item))`, then `None` when finished. The `futures` crate
provides the trait and the adapters (`map`, `filter`, `buffer_unordered`,
`chunks`, `merge`); `tokio-stream` provides constructors such as `ReceiverStream`
and `IntervalStream`. A **`Sink`** is the write side: asynchronous `send`,
`feed`, `flush` and `close`.

```rust
use futures::stream::{self, StreamExt, TryStreamExt};

#[tokio::main]
async fn main() {
    let values = stream::iter(1..=10)
        .filter(|n| futures::future::ready(n % 2 == 0))
        .map(|n| n * n)
        .take(3)
        .collect::<Vec<_>>()
        .await;
    println!("{values:?}");

    // Concurrency inside a stream: at most four futures in flight.
    let pages: Vec<Result<u32, &str>> = stream::iter([1_u32, 2, 3])
        .map(|id| async move { Ok(id * 10) })
        .buffer_unordered(4)
        .try_collect()
        .await
        .unwrap();
    println!("{pages:?}");

    // Wrapping an mpsc receiver as a stream.
    let (tx, rx) = tokio::sync::mpsc::channel(4);
    tokio::spawn(async move {
        for value in 1..=3 {
            tx.send(value).await.unwrap();
        }
    });
    let mut stream = tokio_stream::wrappers::ReceiverStream::new(rx);
    while let Some(value) = stream.next().await {
        println!("stream {value}");
    }
}
```

`StreamExt::next` is not in the standard library; it comes from the extension
trait, so the crate must be in scope. Streams compose well with `select!` and
with backpressure via bounded channels. A `Sink` is usually used directly
through the writer API; for most HTTP and file code the ecosystem exposes
`AsyncWrite` rather than `Sink`, so the sink traits matter mainly in
protocol libraries.

## 2.7 Async traits

Before Rust 1.75, traits could not have `async fn` in a way that worked with
`dyn Trait`. The `async-trait` crate transforms the methods into functions
returning `Pin<Box<dyn Future>>`, which works on older compilers and remains
required for object-safe async traits. Native `async fn` in traits is stable,
but a trait using it is not object-safe by default.

```rust
// Native async fn in a trait: stable since 1.75, not object-safe.
trait Fetcher {
    async fn fetch(&self, url: &str) -> Result<String, String>;
}

struct Http;

impl Fetcher for Http {
    async fn fetch(&self, url: &str) -> Result<String, String> {
        Ok(format!("body of {url}"))
    }
}

// Object-safe variant: the future is boxed and the method has an explicit
// lifetime, or use #[async_trait] to generate this shape.
type BoxFuture<'a, T> = std::pin::Pin<Box<dyn std::future::Future<Output = T> + Send + 'a>>;

trait DynFetcher: Send + Sync {
    fn fetch<'a>(&'a self, url: &'a str) -> BoxFuture<'a, Result<String, String>>;
}

struct DynHttp;

impl DynFetcher for DynHttp {
    fn fetch<'a>(&'a self, url: &'a str) -> BoxFuture<'a, Result<String, String>> {
        Box::pin(async move { Ok(format!("body of {url}")) })
    }
}

async fn use_fetcher(fetcher: &dyn DynFetcher) {
    println!("{}", fetcher.fetch("/").await.unwrap());
}

#[tokio::main]
async fn main() {
    println!("{}", Http.fetch("/native").await.unwrap());
    use_fetcher(&DynHttp).await;
}
```

Use native `async fn` for generic code (`fn run<F: Fetcher>(f: F)`) and for
trait definitions where you do not need `dyn`. Use `async-trait` or the manual
boxed form when you need a `dyn` trait object, because the trait must remain
object-safe. The boxed form allocates one future per call; in a hot path,
consider an enum of concrete implementations instead. `async fn` in traits
also interacts with `Send`: the returned future is `Send` only if everything
held across `.await` is `Send`, which is why the boxed form above adds `+ Send`.

## 2.8 Thread-based concurrency and scoped threads

`std::thread::spawn` runs a closure on a new OS thread. It requires a
`'static` closure, or `std::thread::scope` can lend stack data to threads that
are guaranteed to be joined before the scope ends.

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        thread::sleep(Duration::from_millis(10));
        21 * 2
    });
    println!("{}", handle.join().unwrap());

    let names = vec![String::from("a"), String::from("b"), String::from("c")];
    let total = thread::scope(|scope| {
        let handles: Vec<_> = names
            .iter()
            .map(|name| scope.spawn(|| name.len()))
            .collect();
        handles.into_iter().map(|handle| handle.join().unwrap()).sum::<usize>()
    });
    println!("{total}");
}
```

A panic in a spawned thread does not abort the process by default; it unwinds
that thread and `join()` returns `Err(Box<dyn Any>)`. A scoped thread that
escapes its scope is impossible by construction. Threads are the right tool for
CPU-bound work; for a pool, `rayon` turns a data-parallel loop into work-stealing
threads without a hand-written spawn per item. The [threads chapter](#threads)
covers `available_parallelism`, stack sizes and `thread::Builder`.

## 2.9 Message passing with `std::sync::mpsc`

The standard library's multi-producer, single-consumer channel is synchronous:
`send` blocks when the bound is reached (for `sync_channel`), and `recv` blocks
the calling thread. It is a fine choice in a thread-based program and a poor
choice inside an async task, where blocking would stall the executor.

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(id * 10).unwrap();
        });
    }
    drop(tx);

    let mut values: Vec<_> = rx.iter().collect();
    values.sort_unstable();
    println!("{values:?}");

    let (tx, rx) = mpsc::sync_channel(1); // bounded: send blocks
    thread::spawn(move || {
        for n in 0..3 {
            tx.send(n).unwrap();
        }
    });
    println!("{}", rx.recv().unwrap());
}
```

The channel closes when every sender is dropped; `rx.iter()` then ends.
`tx.clone()` is how the producer count grows, and forgetting to drop the
original `tx` in the main thread is the classic "receiver never terminates"
bug. Tokio's `mpsc` is the async equivalent from section 2.5; cross the
boundary with `tokio::sync::mpsc` or `spawn_blocking`, not with `std::sync::mpsc`
inside an async task.

## 2.10 Shared state: `Mutex`, `RwLock` and `Arc`

Sharing across threads needs shared ownership (`Arc`) plus synchronisation.
`Mutex<T>` gives one writer at a time; `RwLock<T>` gives many readers or one
writer. Both are in `std::sync`; Tokio's `tokio::sync` versions are asynchronous
and must be used when the lock is held across `.await`.

```rust
use std::sync::{Arc, Mutex, RwLock};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0_u64));
    let mut handles = Vec::new();
    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1_000 {
                *counter.lock().unwrap() += 1;
            }
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }
    println!("{}", counter.lock().unwrap());

    let config = Arc::new(RwLock::new(String::from("v1")));
    let reader = Arc::clone(&config);
    let read = thread::spawn(move || reader.read().unwrap().clone());
    config.write().unwrap().push_str("-edited");
    println!("{}", read.join().unwrap());
    println!("{}", config.read().unwrap());
}
```

`Mutex::lock` returns a `MutexGuard`; the lock is released when the guard
drops. A panic while holding the lock marks it **poisoned**, and `unwrap`
propagates that panic. Use `PoisonError::into_inner` if the data is still
usable after a panic. `RwLock` is not automatically faster: it pays for
bookkeeping and can starve writers under a stream of readers. Prefer a channel
when the ownership of the data can move to one task, and prefer atomics for a
single counter or flag. The [shared-state chapter](#shared-state) traces the
futex implementation.

:::warn Holding a `std::sync::Mutex` across `.await`
The future may be moved to another worker thread while the guard is alive, and
the guard is not `Send`; the compiler usually rejects it. Even if it compiled,
the lock would be held while the task is parked, blocking every other task on
that runtime thread. Use `tokio::sync::Mutex` if the critical section must
cross an `.await`, or restructure so it does not.
:::

## 2.11 Atomic types and memory ordering

Atomics provide lock-free operations on a single word. They are the building
blocks of counters, flags, reference counts and lock implementations. The types
are `AtomicBool`, `AtomicUsize`, `AtomicI32`, `AtomicPtr<T>` and friends;
`AtomicU64` is not available on every 32-bit target.

```rust
use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let counter = Arc::new(AtomicUsize::new(0));
    let mut handles = Vec::new();
    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1_000 {
                counter.fetch_add(1, Ordering::Relaxed);
            }
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }
    println!("{}", counter.load(Ordering::Relaxed));

    // Release/Acquire: the flag publishes the data written before the store.
    let data = Arc::new(AtomicUsize::new(0));
    let ready = Arc::new(AtomicBool::new(false));
    let writer = {
        let data = Arc::clone(&data);
        let ready = Arc::clone(&ready);
        thread::spawn(move || {
            data.store(42, Ordering::Relaxed);
            ready.store(true, Ordering::Release);
        })
    };
    while !ready.load(Ordering::Acquire) {
        std::hint::spin_loop();
    }
    println!("{}", data.load(Ordering::Relaxed));
    writer.join().unwrap();
}
```

| Ordering | Guarantees | Use |
| --- | --- | --- |
| `Relaxed` | atomicity only, no ordering between threads | counters where the total is read after joining |
| `Acquire` (load) | later reads/writes stay after the load | consumer of a `Release` store |
| `Release` (store) | earlier reads/writes stay before the store | publisher of data |
| `AcqRel` | both, for read-modify-write | locks and queues |
| `SeqCst` | a single global order across all atomics | when reasoning is hard; the safe default |

The release/acquire pair is what makes "write data, then set a flag" safe: a
thread that sees `true` with `Acquire` is guaranteed to see the 42. With
`Relaxed` on both sides, the data race is gone but the visibility is not
guaranteed. `compare_exchange` builds locks and state machines; watch for the
ABA problem when the value can return to its old state. Section 2.14 extends
these bounds to async tasks.

## 2.12 Deadlock prevention and concurrency patterns

Deadlock occurs when tasks wait on each other in a cycle. The four practical
defences are:

1. **Order the locks.** Always acquire `A` before `B`, never the reverse.
2. **One lock at a time.** Copy the data out, drop the guard, then act.
3. **Bound every wait.** Use `tokio::time::timeout` around operations that
   could block indefinitely.
4. **Prefer ownership transfer.** Send the value to the one task that owns it
   instead of sharing it behind a lock.

```rust
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

fn main() {
    let left = Arc::new(Mutex::new(0));
    let right = Arc::new(Mutex::new(0));

    // Consistent order: every thread takes `left` then `right`.
    let a = {
        let (left, right) = (Arc::clone(&left), Arc::clone(&right));
        thread::spawn(move || {
            let _first = left.lock().unwrap();
            thread::sleep(Duration::from_millis(1));
            let _second = right.lock().unwrap();
        })
    };
    let b = {
        let (left, right) = (Arc::clone(&left), Arc::clone(&right));
        thread::spawn(move || {
            let _first = left.lock().unwrap();
            let _second = right.lock().unwrap();
        })
    };
    a.join().unwrap();
    b.join().unwrap();
    println!("no deadlock");
}
```

Other patterns worth knowing: **actor** (one task owns state, others send
messages), **worker pool** (a bounded queue feeds N workers), **fan-out /
fan-in** (`join_all` or a stream with `buffer_unordered`), **scatter-gather**
(`select!` or `FuturesUnordered`), **circuit breaker** (fail fast after
consecutive errors, section 10.13), and **backpressure** (bounded channels and
`Semaphore`). `tokio::sync::Semaphore` limits concurrency without a lock:
acquire a permit before starting work and let it drop when the work ends.

## 2.13 Work-stealing schedulers

A multi-threaded executor keeps one **run queue per worker** plus a global
injector queue. A new task goes to the local queue; an idle worker **steals**
half of another worker's queue. Work stealing balances load without a central
lock and keeps the common case (LIFO local pops) cache-friendly.

```text
worker 0: [t1 t2 t3 t4]      worker 1: []  ──steal──▶  [t3 t4]
worker 2: [t5 t6]            worker 3: [t7]
```

The scheduler also handles **blocking**: `spawn_blocking` work goes to a
separate pool with its own limit (512 threads by default in Tokio), so a slow
filesystem call cannot consume the async worker pool. Tasks are not pre-empted;
a task that never yields (a long CPU loop, a synchronous call) blocks its
worker. That is why async code must yield at `.await` and why CPU work belongs
on `spawn_blocking` or Rayon. The [async internals
chapter](#concurrency-async-internals) walks through Tokio's scheduler code and
the `LIFO` slot optimisation.

## 2.14 `Send` and `Sync` in async contexts

`Send` means a value may move to another thread; `Sync` means `&T` may be
shared between threads. An async task spawned with `tokio::spawn` must be
`Send + 'static`. The compiler checks this by looking at every value held
across an `.await`: if a non-`Send` type (an `Rc`, a `RefCell` guard, a
`std::sync::MutexGuard`) is alive at a suspension point, the generated future
is not `Send`, and `spawn` rejects it.

```rust
use std::rc::Rc;
use tokio::sync::Mutex;

async fn not_send() {
    let value = Rc::new(1);
    tokio::task::yield_now().await; // Rc is held across the await
    println!("{value}");
}

async fn good() {
    let value = Rc::new(1);
    println!("{value}");
    // The Rc is dropped before the await, so the future can be Send.
    tokio::task::yield_now().await;
}

async fn shared() {
    let data = std::sync::Arc::new(Mutex::new(Vec::new()));
    let mut guard = data.lock().await;
    guard.push(1);
    // The tokio guard is Send, so holding it across an await is allowed here.
    tokio::task::yield_now().await;
    drop(guard);
}

#[tokio::main]
async fn main() {
    // tokio::spawn(not_send()); // error: future cannot be sent between threads
    good().await;
    shared().await;
    println!("ok");
}
```

Ways to fix a non-`Send` future: drop the offending value before the `.await`
(add a scope), replace `Rc` with `Arc`, replace `RefCell` with `Mutex` or
`RwLock`, use `tokio::sync::Mutex` instead of `std::sync::Mutex` when the
guard must cross an await, or use `spawn_local` on a current-thread runtime
when the task genuinely must stay on one thread. Do not reach for
`unsafe impl Send`; it is a promise the compiler could not verify, and async
state machines have subtle drop orders. The [shared-state
chapter](#shared-state) proves the auto-trait rules from the data-race
definition.

:::exercise guided Make this future `Send`
This async function is rejected by `tokio::spawn` because it holds a
`std::rc::Rc` across an `.await`. Fix it in two different ways: one that keeps
single-threaded ownership, and one that makes it `Send`.

```rust
async fn report() {
    let values = std::rc::Rc::new(vec![1, 2, 3]);
    tokio::task::yield_now().await;
    println!("{}", values.len());
}
```
::hint
The first fix ends the borrow of the `Rc` before the `.await`; `usize` is
`Send`. The second replaces `Rc` with `Arc` and clones the handle into the
future. Both preserve the output.
::solution
```rust
async fn report() {
    let length = {
        let values = std::rc::Rc::new(vec![1, 2, 3]);
        values.len()
    };
    tokio::task::yield_now().await;
    println!("{length}");
}

async fn report_shared() {
    let values = std::sync::Arc::new(vec![1, 2, 3]);
    let handle = std::sync::Arc::clone(&values);
    tokio::task::yield_now().await;
    println!("{}", handle.len());
}

#[tokio::main]
async fn main() {
    tokio::spawn(report()).await.unwrap();
    tokio::spawn(report_shared()).await.unwrap();
}
```

:::exercise practice Merge two async streams with backpressure
Create two bounded `mpsc` channels. Spawn one producer per channel, each
sending `1..=5` after a short delay. Merge the two receivers into a single
stream, take the first six values, and print them. Explain why the channel
capacity matters.
::hint
Use `tokio_stream::wrappers::ReceiverStream` and `StreamExt::merge`. The
bounded capacity applies backpressure: a producer waits when the queue is
full, which bounds memory. With an unbounded channel the producer would outrun
the consumer.
::solution
```rust
use std::time::Duration;
use tokio::sync::mpsc;
use tokio_stream::wrappers::ReceiverStream;
use tokio_stream::StreamExt;

#[tokio::main]
async fn main() {
    let (tx_a, rx_a) = mpsc::channel(2);
    let (tx_b, rx_b) = mpsc::channel(2);

    tokio::spawn(async move {
        for n in 1..=5 {
            tx_a.send(n).await.unwrap();
            tokio::time::sleep(Duration::from_millis(1)).await;
        }
    });
    tokio::spawn(async move {
        for n in 10..=15 {
            tx_b.send(n).await.unwrap();
            tokio::time::sleep(Duration::from_millis(2)).await;
        }
    });

    let mut merged = ReceiverStream::new(rx_a).merge(ReceiverStream::new(rx_b));
    let mut seen = Vec::new();
    while let Some(value) = merged.next().await {
        seen.push(value);
        if seen.len() == 6 {
            break;
        }
    }
    println!("{seen:?}");
}
```

:::exercise challenge A bounded worker pool
Write an async worker pool with four workers, a `mpsc` job queue of capacity
eight, and jobs that sleep for `id % 3` milliseconds and return their square.
Collect the results and verify the sum. Then add a `tokio::sync::Semaphore` that
limits concurrency to two and explain what changes.
::hint
Create the channel, spawn four workers each with a cloned receiver via
`Arc<Mutex<Receiver>>` or by using a single receiver in a loop with `select!`.
A simpler design: one dispatcher task owns the receiver and sends jobs to four
worker channels. For the semaphore, wrap each job in a permit acquisition.
::solution
```rust
use std::sync::Arc;
use std::time::Duration;
use tokio::sync::{mpsc, Semaphore};

async fn run_job(id: u64) -> u64 {
    tokio::time::sleep(Duration::from_millis(id % 3)).await;
    id * id
}

#[tokio::main]
async fn main() {
    let (job_tx, mut job_rx) = mpsc::channel::<u64>(8);
    let (result_tx, mut result_rx) = mpsc::channel::<u64>(8);
    let semaphore = Arc::new(Semaphore::new(2));

    let dispatcher = {
        let semaphore = Arc::clone(&semaphore);
        tokio::spawn(async move {
            while let Some(id) = job_rx.recv().await {
                let permit = semaphore.clone().acquire_owned().await.unwrap();
                let result_tx = result_tx.clone();
                tokio::spawn(async move {
                    let value = run_job(id).await;
                    result_tx.send(value).await.unwrap();
                    drop(permit);
                });
            }
        })
    };

    for id in 1..=6 {
        job_tx.send(id).await.unwrap();
    }
    drop(job_tx);
    dispatcher.await.unwrap();
    drop(result_tx);

    let mut total = 0;
    while let Some(value) = result_rx.recv().await {
        total += value;
    }
    println!("{total} {}", total == (1..=6).map(|id| id * id).sum::<u64>());
}
```

The semaphore moves the bound from "one task per job" to "at most two jobs in
flight"; the queue still applies backpressure at eight. Without a bound, a
flood of jobs creates a flood of tasks, each holding a future and its captured
state.
:::

## Quiz

:::quiz Async and concurrency check
? What happens when an `async fn` is called?
- The body runs immediately on the current thread
+ A future is created; the body runs only when the future is polled
- A new OS thread is started
- The future is scheduled on the runtime automatically
= `async fn` is sugar for a function returning `impl Future`. The body is a state machine that starts on the first poll, which `.await`, `join!` or `spawn` provides.

? Why does `tokio::spawn` require `Send`?
- Because all Rust futures are `Send`
+ Because the task may run on any worker thread, so its state must be safe to move between threads
- Because `Send` makes the future faster
- Because the runtime is single-threaded
= The multi-threaded scheduler can migrate a task. A value held across `.await` must therefore be `Send`, and the future must be `'static` because it has no borrow of the spawning stack.

? What is the difference between `join!` and `spawn`?
- `join!` runs on a new thread; `spawn` does not
+ `join!` polls futures concurrently within the current task; `spawn` creates an independent task scheduled by the runtime
- `spawn` requires no runtime
- `join!` can only be used with `Result`
= `join!` waits for all branches in the same task and does not require `Send`/`'static`. `spawn` hands the future to the scheduler and returns a `JoinHandle`.

? Which channel keeps only the latest value for each receiver?
- `mpsc`
- `broadcast`
+ `watch`
- `oneshot`
= `watch` is designed for configuration and shutdown flags: sends replace the current value, and receivers observe the newest state. `broadcast` queues every message per receiver and reports lag.

? What does `Ordering::Release` on a store guarantee?
- Nothing; atomics are always sequentially consistent
+ All reads and writes before the store become visible to a thread that observes the value with `Acquire`
- The store is faster than `Relaxed`
- The value cannot be changed again
= Release/acquire pairs establish happens-before without making every atomic operation globally ordered. `Relaxed` provides atomicity only.
:::

:::recap
- `async fn` returns a lazy future; a runtime polls it and `.await` suspends at pending points.
- `Pin` prevents a future from moving after it may have taken references to itself; most types are `Unpin`.
- A `Waker` tells the executor that a pending task can make progress; one wake per pending return.
- Tokio provides tasks, `join!`, `try_join!`, `select!` and `spawn_blocking`; blocking calls must leave the async pool.
- `mpsc`, `oneshot`, `broadcast` and `watch` cover queueing, replies, events and latest-value state.
- Streams are asynchronous iterators; `Sink` is the write side; extension traits come from `futures`.
- Native `async fn` in traits works, but object-safe async traits need boxed futures or `async-trait`.
- Scoped threads borrow stack data safely; `std::sync::mpsc` is for thread-based programs.
- `Arc<Mutex<T>>` and `Arc<RwLock<T>>` share state; order locks and never hold a blocking guard across `.await`.
- Atomics trade simplicity for control; use `Acquire`/`Release` to publish data and `SeqCst` when unsure.
- Work stealing balances tasks across workers but cannot pre-empt a task that never yields.
- `Send` bounds on async tasks come from every value held across an `.await`.
:::
