LLVM IR names intermediate values without assigning each one to a physical CPU register. The backend later chooses instructions and maps live values onto the limited register set of a target architecture, such as x86-64 or ARM64 (AArch64). This target-specific translation is called **code generation**.

## Starting point: from virtual IR to real silicon

:::analogy Translating sheet music for a specific instrument
LLVM IR is like a universal musical score written on a staff. A pianist and a violinist read the exact same melody, yet their hands press completely different keys or strings. **Code generation** translates the universal score into exact fingerings for one physical chip—either x86-64 keys or ARM64 strings.
:::

The LLVM back-end executes three tightly coupled steps for each function:

1. **Instruction selection:** Maps abstract IR operations (`add`, `load`, `br`) onto real instructions offered by the target CPU (for example, turning `a + b` on x86-64 into `add` or a clever address-math trick `lea`).
2. **Register allocation:** Fits hundreds of IR virtual registers into the CPU's tiny physical register file (16 general-purpose registers on x86-64, 31 on ARM64). When more variables are alive at once than registers exist, the allocator **spills** extras temporarily onto the stack.
3. **Instruction scheduling:** Orders independent instructions to keep execution pipelines busy and minimise waiting on slow memory reads.

## Reading x86-64 assembly (Intel syntax)

Let us read the real optimised x86-64 assembly produced for `(a + b) * 2` under the Linux System V calling convention (where the first two integer arguments arrive in 32-bit `edi` and `esi`, and the return value goes back in `eax`; the full rule set is in [calling conventions and execution](#calling-conventions-execution)):

```asm
add_and_double:
    lea   eax, [rdi + rsi]    ; compute a + b in one step without touching flags
    add   eax, eax            ; multiply by 2 by adding eax to itself
    ret                       ; pop return address from stack and jump back
```

Read every single word of that output—there are only three instructions!

- **`lea eax, [rdi + rsi]`** (*Load Effective Address*): Originally built to calculate array memory addresses (`base + index`), compilers love using `lea` to add two registers and put the answer in a *third* register (`eax`) in a single instruction without clobbering `edi` or `esi`.
- **`add eax, eax`**: Adding a register to itself doubles it (`* 2`) faster (or smaller) than a full hardware integer multiply (`imul`). Notice `eax` is the lower 32 bits of the 64-bit register `rax` (`i32` is 32 bits wide).
- **`ret`**: Pops the 64-bit return address off the top of the stack into `RIP` (the instruction pointer), returning control to `main`.

:::warn Intel syntax vs AT&T syntax
Linux tools like `objdump` default to **AT&T syntax** (`lea (%rdi,%rsi,1), %eax`, putting destination **last** and adding `%`/`$` sigils) unless you pass **`-M intel`** (or **`-C llvm-args=-x86-asm-syntax=intel`** to `rustc`). This guide consistently uses **Intel syntax**, where the **destination comes first**: `mov dst, src` means `dst = src`.
:::

## Comparing x86-64 and ARM64 assembly

On an ARM64 (`aarch64`) Linux server or Apple Silicon Mac, LLVM emits fixed-width 32-bit RISC instructions instead (arguments arrive in `w0` and `w1`, result returns in `w0`):

```asm
add_and_double:
    add   w8, w0, w1          ; w8 = a + b (three-operand instruction!)
    lsl   w0, w8, #1          ; w0 = w8 << 1 (left-shift by 1 bit multiplies by 2)
    ret                       ; jump to address in link register x30
```

| Aspect | x86-64 (Intel syntax) | ARM64 / AArch64 |
|---|---|---|
| Instruction width | Variable: 1 to 15 bytes per instruction | Fixed: every instruction is exactly 4 bytes (32 bits) |
| Typical operand style | Two-operand (`add dst, src`); memory allowed in ALU ops | Three-operand (`add dst, a, b`); strict load/store (only `ldr`/`str` touch memory) |
| Argument registers (first 2 ints) | `rdi`/`edi`, `rsi`/`esi` | `x0`/`w0`, `x1`/`w1` |
| Return register | `rax`/`eax` | `x0`/`w0` |
| Return address on `call`/`bl` | Pushed onto stack in RAM | Saved into link register `x30` (`LR`) |

## From assembly mnemonics to raw machine code bytes

:::plain Assembly vs machine code
**[[Assembly]]** (`lea eax, [rdi + rsi]`) and **[[machine code]]** (`8d 04 37`) are not two different programming levels—they are two spellings of the **exact same CPU instructions**. Assembly uses short English words (*mnemonics*) and [[register]] names for humans; machine code is the raw sequence of numeric [[opcode]] bytes that the CPU actually fetches from memory.
:::

The **assembler** (built right into LLVM or invoked as `as`) replaces every mnemonic and register name with exact binary opcodes.

Let us inspect the real bytes generated for `int add(int a, int b) { return a + b; }` via `objdump -d -M intel`:

```text
0000000000001160 <add>:
    1160:   8d 04 37             lea    eax, [rdi+rsi*1]
    1163:   c3                   ret
```

Look at those four hexadecimal bytes (`8d 04 37 c3`):

- `0x8d` is the x86-64 [[opcode]] byte for `LEA`.
- `0x04` is the **ModR/M** byte saying "destination is `eax` (`000`) and source uses an indexed SIB byte (`100`)".
- `0x37` is the **SIB (Scale-Index-Base)** byte encoding `rdi` (base `111`) + `rsi` (index `110`) * 1.
- `0xc3` is the single-byte opcode for `RET`.

## Memory, execution, OS, and hardware view

1. **Memory perspective:** Those exact four bytes (`8d 04 37 c3`) live inside the `.text` executable section of your program binary on disk — the section table that names it is [ELF](#linking-elf) — and are mapped read-execute (`R-X`) into virtual RAM when the program runs, exactly as [virtual memory](#virtual-memory-address-spaces) shows in `/proc/self/maps`.
2. **Execution perspective:** The CPU fetches `8d 04 37` from L1i cache, decodes it into an internal micro-operation (`LEA`) — the decode stage is [the ISA and opcode chapter](#isa-opcodes-control-flow) — reads `rdi` and `rsi` from the register file, adds them in the ALU, writes `eax`, then executes `c3` (`ret`) to return.
3. **OS & hardware perspective:** Neither the Linux kernel nor RAM knows the name `add_and_double` during execution—they only see executable memory pages and raw bytes flowing into the CPU instruction decoder.

## Practical experiment: emit assembly and disassemble machine bytes

Try compiling any small Rust file to Intel assembly and object code, then disassembling it with `objdump`:

```sh
$ rustc --emit=asm -C opt-level=3 -C llvm-args=-x86-asm-syntax=intel demo.rs
$ rustc -C opt-level=3 demo.rs -o demo
$ objdump -d -M intel demo | grep -A 15 "<.*add_and_double"
```

Compare `-C opt-level=0` (verbose stack spills, overflow panic checks, frame pointers) against `-C opt-level=3` (a handful of crisp register-only instructions!).

:::compare Intel vs AT&T x86-64 vs ARM64 assembly syntax
| Syntax | Move 42 into return register | Add first two args | Default in |
|---|---|---|---|
| **Intel x86-64** | `mov eax, 42` (`dst, src`) | `lea eax, [rdi+rsi]` | `rustc -C llvm-args=-x86-asm-syntax=intel`, `objdump -M intel` |
| **AT&T x86-64** | `movl $42, %eax` (`src, dst`) | `leal (%rdi,%rsi), %eax` | Traditional GNU `as` / `objdump` default |
| **ARM64 (AArch64)** | `mov w0, #42` (`dst, #imm`) | `add w0, w0, w1` | Apple Silicon, AWS Graviton, Raspberry Pi 64-bit |
:::

:::recap
- LLVM code generation performs **instruction selection**, **register allocation**, and **instruction scheduling** for a specific CPU target.
- Assembly uses human-readable mnemonics (`mov`, `lea`, `add`, `lsl`, `ret`) that correspond directly to numeric **machine code** bytes.
- x86-64 uses variable-length (1–15 byte) CISC instructions; ARM64 uses fixed 4-byte load-store RISC instructions.
- `rustc --emit=asm` prints assembly, and `objdump -d -M intel` displays both the hex machine bytes and their decoded mnemonics side by side.
:::

:::exercise guided Decode a tiny assembly listing
Look at this x86-64 Intel assembly for `fn mystery(x: i32) -> i32`:
```asm
mystery:
    imul  eax, edi, 3
    add   eax, 1
    ret
```
What Rust expression does `mystery` compute?
::hint
Remember the first `i32` argument arrives in `edi`, and the `i32` return value leaves in `eax`. `imul dst, src, imm` multiplies `src` by `imm` and puts the result in `dst`.
::solution
```rust run
#[inline(never)]
fn mystery(x: i32) -> i32 {
    x * 3 + 1
}

fn main() {
    println!("mystery(10) = {}", mystery(10));
}
```
```output
mystery(10) = 31
```

`imul eax, edi, 3` computes `x * 3` into `eax`, then `add eax, 1` adds `1`, and `ret` returns `eax = 31`.

:::exercise practice Compare debug vs release overflow behaviour
Write a small Rust function `square(x: u32) -> u32 { x * x }` and a wrapping variant `square_wrap(x: u32) -> u32 { x.wrapping_mul(x) }`. Explain why debug builds generate noticeably more assembly instructions for `square` than for `square_wrap`, while release builds generate the exact same `imul` instruction for both.
::hint
Think about checked overflow panics in debug builds versus wrap-around semantics in release builds.
::solution
```rust run
fn square(x: u32) -> u32 {
    x * x
}

fn square_wrap(x: u32) -> u32 {
    x.wrapping_mul(x)
}

fn main() {
    println!("{} {}", square(12), square_wrap(12));
}
```
```output
144 144
```

In debug builds, `x * x` checks the CPU's overflow flag (`jo`—jump if overflow) and branches to `core::panicking::panic` if the product exceeds `u32::MAX`. In release builds (`--release`), Rust does not insert runtime overflow panic checks for `+`/`*`, so both functions lower to the identical unsigned multiply instruction.
:::

:::exercise challenge Shift-and-add multiplication
Compilers often replace multiplication by constants like `* 5` with a single `lea` instruction (`lea eax, [rdi + rdi*4]`) instead of `imul`. Write a Rust helper `times_five_bitshift(x: u32) -> u32` using only bit-shifting (`<<`) and addition (`+`), and test it on `0`, `7`, and `42`.
::hint
Remember `x << 2` equals `x * 4`, because shifting left by 2 bits multiplies by `2² = 4`.
::solution
```rust run
fn times_five_bitshift(x: u32) -> u32 {
    (x << 2) + x
}

fn main() {
    for n in [0, 7, 42] {
        println!("{n} * 5 = {}", times_five_bitshift(n));
    }
}
```
```output
0 * 5 = 0
7 * 5 = 35
42 * 5 = 210
```

Because `x * 5 = x * 4 + x = (x << 2) + x`, both hardware shift-add logic and x86-64's `[rdi + rdi*4]` addressing mode execute `* 5` without engaging the integer multiplier circuit!
:::
