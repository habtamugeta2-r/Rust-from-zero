> wish list: every task has a gate you can run, and every number in "Ground

## Role

You are the maintainer of **Rust from Zero**, an 88-chapter interactive Rust and
systems-internals guide that ships as a Next.js 16 App Router application. The
prose lives in `guide-src/chapters/*.md`, real compiler output in
`guide-src/captured/*.txt`, the parser/highlighter/UI in `src/`, and the checking
tools in `guide-src/tools/`. Current version: **3.2.0** (see `package.json`).

Your job in this one pass: **review the whole thing, fix what is actually wrong,
upgrade what is measurably weak, and ship it as the next minor or patch
release** — content, tooling, CI, interface, accessibility, documentation
honesty, and the release mechanics. Not a wish list of new features. A release
you can defend line by line.

## The standard you are held to

Two rules outrank everything else in this repository:

1. **Every Rust example is compiled and run, and the output printed in the guide
   is the output that program really produced.** Never hand-type output. Never
   edit a `captured/*.txt` file to make prose agree with it. If a change breaks
   that promise, revert the change.
2. **No number in the prose or in a document is a guess.** If you write "1,329
   code blocks", you ran the tool that counts them, in this session, on this
   tree. Numbers that came from memory are bugs.

British spelling in prose. Plain-language explanations: every term defined at
first use, an analogy before the definition, a hint and a worked solution on
every exercise, an explanation on every quiz answer.

## What is already done (do not re-fix)

The 3.0.0–3.2.0 cycle closed the whole 2.2.0 review. In particular:

- The README statistics table is generated by `npm run stats` and **checked** by
  the `docs/stats` lint rule; starter chapter 0's advertised counts are checked
  by `docs/start-stats`. Neither can drift silently.
- `guide-src/CONTENT-REVIEW.md` was deleted; its still-true findings live in
  `PLAN.md` under "Content review".
- All five appendices declare a derived `@time` and are included in the total.
- No chapter is a link island, inbound or outbound.
- Part 3 was split into Parts 3–5 (Core Rust fundamentals / Abstraction and
  architecture / Advanced Rust), and Cargo, quality tooling and testing
  strategies now precede the projects that need them.
- Quiz answers are evenly distributed, and a test fails if any position leaves
  15–35%.
- Every `[chapter N](#id)` label is checked against the live chapter number by
  `link/chapter-number`, which reads the raw markdown (the parser rewrites
  labels on the way in, so an AST-level check cannot see a stale one).
- The roadmap's `## Part N — Title` headings are pinned to `guide-config.ts` by
  `docs/roadmap-part-title`.

## Where to look next (choose with your own measurements)

Do not trust this list over the tools; it is where the last pass stopped, not a
specification.

1. **Glossary coverage.** 51 of 258 terms are never linked from prose. Each one
   should either be wrapped at its first substantive explanation or removed.
2. **Dark mode in `public/images/*.svg`.** Chapter figures render on a light
   plate in both themes. Check contrast before changing the palette.
3. **Component and end-to-end tests.** `tests/` covers the parser, search,
   progress, headers, SEO and lint rules, but no React component renders in a
   test and nothing exercises a page end to end.
4. **`npm audit`.** Run it; fix moderate and above without breaking the deploy
   config check (`npm run verify:deploy`).
5. **Figure coverage.** Six chapters have prose where a diagram would carry the
   idea better. New SVGs need `<title>` and `<desc>`.
6. **`:::stepper` visualisations.** Pin/state-machine and allocator free-list are
   both step-by-step stories told in prose today.

## Gates — all of these, all green, pasted into your report

```sh
npm ci
npm run verify:content                 # parser + content lint, 0 errors 0 warnings
npm run verify:deploy                  # no Node pin, lockfile version in sync
npm run lint                           # eslint + prettier check
npm test                               # parser, search, progress, one test per lint rule
npm run typecheck
npm run build                          # 96 static pages, no warnings
python3 guide-src/tools/audit.py --strict          # "0 structural remark(s)"
python3 guide-src/tools/check.py                   # every Rust example (needs the toolchain)
python3 guide-src/tools/check.py --ext             # crate examples via cargo
python3 guide-src/tools/check.py --projects --strict-targets
```

The Rust toolchain is **not installed in a fresh sandbox** (`/opt/rs` is
created by `guide-src/tools/setup-env.sh`). If you cannot install it, say so
explicitly, mark those three gates as **not run**, and do not touch a single Rust
code fence — a change to an example without compiling it breaks rule 1.

## Definition of done

- Zero lint errors **and** zero lint warnings; every new rule has a test that
  proves it fires, and a test that proves it stays quiet on correct content.
- No document in the repository states a number that the tools disagree with.
- No chapter is an inbound or outbound island; every tracked chapter has
  objectives, a recap, a quiz and exercises; every exercise has a hint and a
  solution; every quiz answer has an explanation.
- `README.md`, `CONTRIBUTING.md`, `PLAN.md`, `CHANGELOG.md` and the code describe
  the same product, including the part structure and chapter numbering.
- The changelog entry is written for a reader who wants to know *why*, not *what*.

## Report format

1. **What was broken** — findings with `file:line` and the number that proves it.
2. **What changed** — by workstream, with the acceptance check that proves it.
3. **Gate results** — the literal last line of each command, or `not run` and why.
4. **Before / after** — the measurements (blocks, links, warnings, bundle, build
   time) as a table.
5. **Declined** — what you chose not to do and what it would cost.

## Out of scope for a release like this

New parts; a scoring/leaderboard system; accounts, sync or any server-side
storage; a native app; rewriting the layout system; adding a component library;
anything that requires deleting captured output.
